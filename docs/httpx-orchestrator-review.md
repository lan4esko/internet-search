# Разбор Bash-оркестратора httpx

Разобран пользовательский скрипт из приложения к сообщению. Скрипт читает готовые файлы URL в каталоге `output/<country>`, последовательно запускает httpx для каждого файла, сохраняет совпадения в `alive-forti/<country>` и ведёт `progress.json`. Masscan, разбор его JSON и создание входных чанков остаются предыдущим этапом.

## Фактические условия поиска

Запрашиваются три пути: `/remote/login`, `/remote/index`, `/ssl-vpn/login.html`. Повторные `-match-string` в используемом проектом httpx 1.12.0 накапливаются и работают как **OR**, без учёта регистра:

- `ftnt-fortinet-grid`;
- `name="magic"`;
- `SVPNCOOKIE`.

Поиск происходит по raw HTTP-ответу, включающему заголовки и тело. Поэтому cookie в `Set-Cookie` также подходит. Это проверено по [разбору аргументов](https://github.com/projectdiscovery/httpx/blob/v1.12.0/runner/options.go) и [проверке результата](https://github.com/projectdiscovery/httpx/blob/v1.12.0/runner/runner.go), а также локальным экспериментом с настоящим бинарником и отключённой внешней сетью: три страницы с разными маркерами прошли, страница без маркеров — нет.

`MAX_THREADS=500` задаёт параллельность внутри одного процесса. Файлы обрабатываются последовательно. Параллельности 500 недостаточно для оценки скорости: дополнительно действует rate-limit httpx. `DEBUG=false` ни разу не используется и не включает диагностический режим.

Скрипт использует общие редиректы `-follow-redirects`. Протокол явно не закреплён: возможна штатная подмена HTTPS на HTTP при неудаче. В нашем проекте входные URL формируются с выбранной схемой, включён `-no-fallback-scheme`, редиректы ограничены исходным хостом. Режимы описаны в [документации httpx](https://docs.projectdiscovery.io/opensource/httpx/usage).

## Критичные ошибки оркестрации

| Ситуация | Текущее поведение | Требуемое поведение |
| --- | --- | --- |
| `timeout` сработал, бинарник отсутствует или завершился ошибкой | `|| true` скрывает код завершения; stderr уничтожается; файл безусловно помечается completed | Сохранить код и диагностику; различать completed, partial, timeout и failed; ошибочный чанк повторять |
| Файл лежит во вложенном подкаталоге | Рекурсивный `find` возвращает basename; восстановленный путь теряет подкаталог | Сохранять полный или относительный путь без потери структуры |
| Содержимое файла или параметры поиска изменились | Журнал проверяет только country + filename и пропускает старое имя | Использовать checksum входа и hash профиля |
| Запущены две копии оркестратора | Обе могут менять progress.json и убивать чужие httpx по общему шаблону | Атомарный захват чанка, владелец и lease; хранить PID конкретного дочернего процесса |
| Частичный результат уже существует | Перед повтором выполняется `rm`; затем частичный новый вывод может стать окончательным | Сохранять артефакты попыток; публиковать финальный результат после подтверждённого завершения |
| Требуется объяснить нулевой результат | Хранятся только прошедшие matcher URL, все сообщения процесса отбрасываются | Сохранить исходные ответы, ошибки запросов и результаты правил |

Таймаут считается по строкам, но три пути увеличивают число базовых проверок втрое. Например, 100 000 входов дают минимум 300 000 проверок. При лимите 150/с только отправка занимает минимум 2000 секунд, а формула скрипта даёт 1860; сетевые таймауты, повторы и редиректы дополнительно увеличивают время. Для больших файлов потолок 3600 секунд также не гарантирует обработки всего входа.

`grep -c ... || echo 0` при отсутствии подходящих строк выдаёт два нуля (`0\n0`), что ломает арифметику. Счётчик `wc -l` считает переводы строк: единственная строка без завершающего LF может быть ошибочно признана пустым файлом. `wc -l` также учитывает мусорные строки, а предварительный grep — только строки с http/https. Нужен единый разбор и счётчик валидных входов.

Порт берётся из имени файла до первого дефиса. Это работает только при жёстком соглашении `10443-0.txt`; имя `targets.txt` породит некорректный порт. Дедупликация выполняется внутри файла, поэтому общий счётчик находок может включать повторы. Экспорт проекта берёт IP и исходный порт из БД и объединяет endpoints по всему запуску.

Статистика `found_count / elapsed` показывает скорость находок, а не интенсивность запросов или число обработанных целей. Пропущенные по progress.json файлы не входят в processed_files, поэтому итоговый счётчик после возобновления может не достигнуть total_files.

Команды установки locale не восстанавливают уже утраченный текст: знаки `?` в комментариях и сообщениях присутствуют в самом предоставленном файле. Логика основных команд читается независимо от этих сообщений.

## Перенос в текущий проект

Практическую часть скрипта стоит перенести как новый профиль: три пути и OR по маркерам. Для cookie нужны правила по `Set-Cookie` и, при необходимости, телу. `status_code=200` нельзя добавлять отдельным OR-правилом: оно пропустит любую успешную страницу. Сохранённый профиль уже созданного запуска остаётся неизменным.

Маркер `name="magic"` сам по себе означает кандидата: это обычное имя HTML-поля, не исключительное доказательство производителя. Для подтверждённой системы нужно сохранять сочетание признаков и исходный ответ.

Реализованный debug-режим оставляет фактические аргументы, raw Masscan JSON, очищенные IP:PORT, входные URL каждого HTTP-чанка, raw HTTP JSONL и счётчики. CIDR не раскрываются в список IP; перед записью discoveries проверяются TCP, принадлежность сети части, выбранный порт и уникальность endpoint.

Захват текущего запуска подтвердил исходящие SYN Masscan и TLS ClientHello httpx. В изученных HTTP-потоках встречных TLS-данных нет. Такая ситуация предшествует HTTP-запросу и оценке маркеров; смена строк поиска сама по себе не устраняет отсутствие TLS-ответа.
