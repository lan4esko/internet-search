# Публикация и выпуск на GitHub

Git хранит исходники, миграции, шаблоны профилей, тесты и инструкции. Состояние
рабочей установки хранится отдельно: `.env`, пароли, загруженные CIDR, результаты,
дампы трафика и тома Docker не должны попадать в репозиторий. Публикация кода
не переносит control или физические TASK-базы; для нового сервера применяются
чистые PostgreSQL тома и [инструкция TASK](task-operations.md).

## Первоначальная публикация

Нужен GitHub CLI `gh` и авторизация владельца. Установите CLI по
[официальной инструкции](https://cli.github.com/), затем выполните:

```bash
gh auth login --hostname github.com --git-protocol https --web
python3 scripts/check_repository.py
git status --short
git log -5 --oneline
gh repo create OWNER/internet-search --private --source=. --remote=origin --push
```

Замените `OWNER` своим логином или организацией, где есть право создания
репозитория. Для публичного проекта нужно осознанно выбрать `--public`.
Пароль и токен не вставляются в файлы проекта или команду remote.
Команда `gh repo create` создаёт репозиторий и отправляет существующие коммиты;
подробности — [GitHub CLI](https://cli.github.com/manual/gh_repo_create).

Эта версия проекта публикуется с заново созданной историей: прежняя история
учебного прототипа в рабочем каталоге не используется. Если `origin` или
удалённый репозиторий уже существуют, сначала проверьте их владельца и URL;
перезаписывать чужой репозиторий нельзя. Перед публикацией просмотрите
`git diff --cached` и историю: автоматическая
проверка распознаёт лишь некоторые форматы секретов, а `.gitignore` не удаляет
данные из уже созданных коммитов. Незакоммиченные файлы не попадут на сервер.

## Проверки и версии

`.github/workflows/ci.yml` проверяет модульные тесты, миграции, создание TASK и
панель в Chromium. Во время CI используются только локальные тестовые адреса;
интернет-сканирование не запускается.
Проверки запускаются при push, pull request и вручную. Workflow получает только
право чтения содержимого; шаг checkout закреплён за конкретным commit SHA.

После успешного CI выберите номер версии и пометьте проверенный коммит:

```bash
git tag -a v0.1.0 -m 'Первая проверенная версия для развёртывания'
git push origin v0.1.0
gh release create v0.1.0 --title 'Internet Search v0.1.0' --notes-file CHANGELOG.md
```

Это пример будущего выпуска, а не утверждение, что тег уже создан. Release
не должен содержать рабочие CIDR, экспорт найденных систем, `.env` или backup.
Для внешних участников включите защиту `main` с обязательными проверками CI.
Выбор лицензии остаётся за владельцем; лицензия автоматически не назначается.

## Другой сервер

Установите Git, Python 3 и Docker Engine с Compose v2 по
[инструкции развёртывания](deployment.md). Для закрытого репозитория используйте
собственную авторизацию GitHub либо ключ развёртывания с правом чтения.

```bash
git clone https://github.com/OWNER/internet-search.git
cd internet-search
git checkout v0.1.0
python3 scripts/bootstrap.py
```

Указывать тег следует после его публикации. Bootstrap создаёт отдельную
конфигурацию сервера и новые тома. Доступ к панели и включение разрешённого
сканирования описаны в инструкции; копировать `.env` в Git не требуется.
